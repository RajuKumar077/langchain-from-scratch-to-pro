3. Chapter Flow Explanation

Ch.2 opens by stating the real problem is quantity — too much data to fit one prompt. Embeddings are taught conceptually (sparse → dense → cosine similarity) before any code, then the four-step ingestion pipeline (load → split → embed → store) is built step by step, with indexing optimization introduced last, once the "naive" pipeline's weaknesses are exposed. Ch.3 shifts to runtime: retrieval and generation shown simply first, then four production questions are posed, structuring the rest of the chapter around query transformation (fixing the query text), routing (picking the source), and construction (translating to a source's native query language).

Topic: The Goal — Picking Relevant Context for LLMs ⭐☆☆☆☆

Two limitations of LLM knowledge (verbatim): Private data (not in training data by definition) and current events (the knowledge cutoff — training is too costly/slow to stay current).

Two-step solution: (1) Indexing — preprocess documents for easy search (Ch.2). (2) Retrieving — pull relevant data as context at query time (Ch.3).

Topic: Embeddings Before LLMs ⭐⭐☆☆☆

Pre-LLM bag-of-words technique: count word occurrences per sentence across a vocabulary → sparse embeddings (mostly zeros). Book example: three sentences about sunny days converted into a word-frequency table (Table 2-1). Used for keyword search and spam classification.

Limitation: No awareness of meaning — "sunny day" and "bright skies" share no words despite similar meaning.

Topic: LLM-Based Embeddings ⭐⭐☆☆☆

Embedding models trained similarly to LLMs but dedicated to producing numeric representations → dense embeddings (100–2,000 floats, mostly nonzero). Key rule: embeddings from different models can never be combined/compared, even if sizes match.

Topic: Semantic Embeddings Explained ⭐⭐⭐☆☆

Book's lion/pet/dog example (Figures 2-2, 2-3) shows semantically similar words land close in vector space. Cosine similarity = dot product ÷ product of magnitudes → range −1 to 1 (0 = no correlation, 1 = identical, −1 = opposite). Book example: pet–dog ≈ 0.75, pet–lion ≈ 0.1.

Additional Interview Knowledge (book sidebar): Distance = similarity; clustering finds topics; averaging embeddings summarizes a document; vector arithmetic (king − man + woman ≈ queen); multimodal embeddings exist (image/video/sound). Uses: search, clustering, classification, recommendation, anomaly detection.

Topic: Converting Your Documents into Text ⭐⭐☆☆☆

3-step loader pattern: (1) Pick the loader for your document type (2) Instantiate with config (3) Call .load() → list of Document objects.

Named loaders: TextLoader (.txt), WebBaseLoader/CheerioWebBaseLoader (HTML, needs beautifulsoup4/cheerio), PyPDFLoader/PDFLoader (PDF, needs pypdf/pdf-parse). Also: .csv, .json, Markdown, Slack, Notion.

Context window: The hard token limit on input+output for LLMs/embedding models (e.g., 8,192 tokens) — the reason a 100,000+ character PDF must be split next.

Topic: Splitting Your Text into Chunks ⭐⭐⭐☆☆

RecursiveCharacterTextSplitter 4-step algorithm: (1) ordered separators — paragraph \n\n, line \n, word (2) split by paragraph first to respect chunk_size (3) fall back to smaller separators if still too long (4) emit each chunk as a Document with position metadata. Params: chunk_size=1000, chunk_overlap=200.

Language-aware: .from_language(language=Language.PYTHON, ...) uses code keywords as separators (keeps functions intact); supports Python, JS, Markdown, HTML. create_documents() accepts raw strings + optional metadata list.

Topic: Generating Text Embeddings ⭐⭐☆☆☆

Embeddings class interfaces OpenAI/Cohere/Hugging Face: embed_documents() (list→list of vectors), embed_query() (string→vector). Best practice: embed multiple documents at once — more efficient than one at a time.

Topic: Storing Embeddings in a Vector Store (PGVector) ⭐⭐⭐☆☆

Stated disadvantages of dedicated vector stores: relatively new/unproven; steep learning curve; separate DB adds complexity. PGVector solves this by adding vector capability directly into PostgreSQL.

Docker setup (verbatim):

docker run --name pgvector-container \
  -e POSTGRES_USER=langchain -e POSTGRES_PASSWORD=langchain \
  -e POSTGRES_DB=langchain -p 6024:5432 -d pgvector/pgvector:pg16

Core API: PGVector.from_documents(documents, embeddings_model, connection=connection), db.similarity_search("query", k=4), db.add_documents([...], ids=[...]), db.delete(ids=[...]).

Tracking Changes to Your Documents

Problem: re-indexing changed data risks costly recomputation + duplicates. Solution: indexing API with SQLRecordManager, tracking per document: hash (content+metadata), write time, source ID.

Topic: MultiVectorRetriever ⭐⭐⭐⭐☆

Problem (verbatim): a document mixing text and tables can't simply be chunked — a table can be easily lost. Solution: decouple the document for answer synthesis from the reference used for retrieval (Fig 2-5).

Flow: (1) LLM-generate summaries via summarize_chain.batch(chunks, {"max_concurrency": 5}) (2) store summaries + doc_id in vector store (3) store full original chunks in a separate InMemoryStore docstore keyed by same doc_id (4) MultiVectorRetriever(vectorstore=..., docstore=..., id_key="doc_id") — .vectorstore.similarity_search() returns summaries, but .invoke() returns full original chunks.

Topic: RAPTOR ⭐⭐⭐⭐⭐

Definition (verbatim): "Recursive abstractive processing for tree-organized retrieval" — creates summaries capturing higher-level concepts, embeds/clusters them, summarizes each cluster, recursively (Fig 2-6). Source: Sarthi et al., ICLR 2024.

Problem solved: RAG must handle both low-level (single-document fact) AND high-level (cross-document theme) questions — a challenge for typical k-NN retrieval over chunks.

Topic: ColBERT ⭐⭐⭐⭐⭐

Problem (verbatim): fixed-length embeddings compress text, and embedding irrelevant/redundant content may cause hallucination.

3-step solution: (1) contextual embeddings per token, query and document (2) similarity between each query token and all document tokens (3) sum the maximum similarity per query token across document tokens = document score.

Code: Uses RAGatouille — RAGPretrainedModel.from_pretrained("colbert-ir/colbertv2.0"), .index(...), .search(query=..., k=3), .as_langchain_retriever(k=3). Source: Santhanam et al., ColBERTv2.

Topic: Introducing Retrieval-Augmented Generation ⭐⭐☆☆☆

Term coined by Meta AI (Lewis et al., 2021) — RAG models are more factual/specific. Book's FIFA World Cup example shows outdated answer (France 2018) fixed by pasting correct Wikipedia context (Argentina 2022).

Three RAG stages: Indexing (Ch.2) → Retrieval → Generation.

Topic: Retrieving Relevant Documents ⭐⭐☆☆☆

db.as_retriever() abstracts embedding the query + similarity search. search_kwargs={"k": 2} controls result count.

Explicit warning: more documents is NOT always better — slower app, larger/costlier prompt, higher chance of irrelevant chunks causing hallucination.

Topic: Generating LLM Predictions Using Relevant Documents ⭐⭐☆☆☆

Pattern: ChatPromptTemplate with {context}/{question} → prompt | llm. Encapsulate as a single @chain/RunnableLambda function qa for a one-call RAG pipeline; can return {"answer":..., "docs":...}.

Four production questions posed: (1) handling poor user input (2) routing to multiple sources (3) translating NL to target query language (4) optimizing indexing.

Topic: Rewrite-Retrieve-Read ⭐⭐⭐☆☆

Microsoft Research technique (Ma et al., 2023) — LLM rewrites the query before retrieval. Book demo: a distracted rambling query makes basic RAG fail entirely; a rewrite_prompt generating a cleaner search query (ending in **) fixes it.

Downside: extra latency from two sequential LLM calls.

Topic: Multi-Query Retrieval ⭐⭐⭐☆☆

LLM generates multiple query variants → parallel retrieval → combine. Best for questions needing multiple perspectives. get_unique_union() dedupes by page_content as dict key; retriever.batch runs variants in parallel.

Topic: RAG-Fusion ⭐⭐⭐⭐☆

Multi-query + Reciprocal Rank Fusion (RRF) reranking (Rackauckas, 2024). Formula: sum 1/(rank+k) per document across all query lists, sort descending. Uses rank not raw score — robust across different score scales.

Topic: Hypothetical Document Embeddings (HyDE) ⭐⭐⭐⭐☆

Gao et al., 2022 — LLM generates a hypothetical answer; that passage's embedding (not the question's) drives retrieval, since it's more similar to real relevant documents (Fig 3-7). retrieval_chain = generate_doc | retriever.

Topic: Logical Routing ⭐⭐⭐☆☆

Function-calling LLM (e.g., GPT-3.5 Turbo) picks from a defined Literal list of data sources via Pydantic RouteQuery + with_structured_output. choose_route() uses case-insensitive substring match — explicitly for resilience against imperfect LLM output.

Topic: Semantic Routing ⭐⭐⭐☆☆

Embeds route-representative prompts (e.g., physics professor, mathematician) + the query, picks the route via cosine_similarity(...).argmax().

Topic: Text-to-Metadata Filter ⭐⭐⭐⭐☆

SelfQueryRetriever + AttributeInfo (name/description/type per field) translate NL into a metadata filter + semantic query. 4-step mechanism: prompt LLM → parse filter+query → convert filter to vector-store format → filtered similarity search.

Topic: Text-to-SQL ⭐⭐⭐⭐☆

Two strategies: (1) database description via CREATE TABLE + example rows (Rajkumar et al., 2022) (2) few-shot question-query examples. Code: create_sql_query_chain(llm, db) → QuerySQLDatabaseTool(db=db).

Security (verbatim, non-exhaustive): read-only DB user; scope to specific tables only; add query timeouts.

Cheat Sheet

CH.2 — INDEXING
Goal: pick relevant context (quantity problem)
Embeddings: sparse (bag-of-words) -> dense (LLM-based) -> cosine similarity
Pipeline: Loaders -> RecursiveCharacterTextSplitter -> Embeddings -> PGVector
PGVector: from_documents() / similarity_search() / add_documents() / delete()
Tracking changes: SQLRecordManager + index(cleanup="incremental"|"full"|None)
Indexing optimization:
  MultiVectorRetriever -> multi representations -> 1 parent doc
  RAPTOR -> recursive cluster+summarize tree
  ColBERT -> per-token embeddings + MaxSim

CH.3 — RETRIEVAL & GENERATION
RAG stages: Indexing -> Retrieval -> Generation
as_retriever(search_kwargs={"k": N}) -- more docs != better
Query Transformation:
  Rewrite-Retrieve-Read -> LLM rewrites query
  Multi-Query -> N variants, dedupe
  RAG-Fusion -> N variants + Reciprocal Rank Fusion
  HyDE -> embed hypothetical ANSWER
Query Routing:
  Logical -> function-calling LLM picks from Literal list
  Semantic -> cosine similarity vs. route prompt embeddings
Query Construction:
  Text-to-Metadata Filter -> SelfQueryRetriever + AttributeInfo
