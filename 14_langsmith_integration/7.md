# 1. The Core Concept: Feedback Loop

Imagine you've built an AI customer support chatbot.

A customer asks:

> "Why was ₹999 charged to my account?"

The AI responds with an answer, but the answer doesn't explain the charge. The customer clicks 👎 **Not Helpful**.

Now, what should your application do?

It should:

1. Identify which AI execution produced that response.
2. Record the customer's negative feedback against that exact execution.
3. Send that execution to a human-review queue.
4. Allow an engineer to investigate what went wrong.

**That's the entire purpose of this lesson.**

Without this feedback loop, you might know that your AI generated a response, but you wouldn't have an organized way to identify bad responses, collect feedback, and prioritize them for human review.

Your code follows this workflow:

**Step 1 → Execute the LLM**

The user submits a question, and your LangChain application generates a response using Ollama.

**Step 2 → Capture the `run_id`**

LangSmith tracing identifies the particular execution.

**Step 3 → Record user feedback**

The application records whether the user liked or disliked the response.

**Step 4 → Make a triage decision**

If the feedback is negative, the application flags the execution for review.

**Step 5 → Send it to an Annotation Queue**

The problematic execution is added to a LangSmith queue where a human can inspect it.

# 3. The Five Core Components

### Component 1: LLM Execution

Your function:

```python
def run_application_and_capture_id(user_query: str) -> tuple[str, str]:
```

**What does it do?**

It accepts a user's question, executes your LLM chain, and returns two things:

* `run_id`: The identifier for the LLM execution.
* `response`: The answer generated by the LLM.

Your chain is:

```python
chain = prompt | llm | StrOutputParser()
```

Think of it as an assembly line:

| Component           | Responsibility                               |
| ------------------- | -------------------------------------------- |
| `prompt`            | Prepares the instructions and user question. |
| `llm`               | Generates the answer using Ollama.           |
| `StrOutputParser()` | Extracts the response as a string.           |

For example:

```text
User Question
     ↓
Prompt
     ↓
Ollama LLM
     ↓
Output Parser
     ↓
Generated Answer
```

### Component 2: Run ID Capture

This is one of the most important concepts in the lesson.

```python
with collect_runs() as cb:
    response = chain.invoke(
        {"query": user_query},
        config={
            "run_name": "Customer Support Query",
            "tags": ["production-traffic", "support-bot"],
            "metadata": {
                "customer_tier": "enterprise",
                "channel": "web_chat"
            }
        }
    )

    run_id = str(cb.traced_runs[0].id)
```

**What is a `run_id`?**

Imagine your chatbot handles 10,000 customer queries every day.

How would you identify the exact AI execution that produced a particular bad response?

You need a unique identifier for that execution: the `run_id`.

For example:

```text
Customer Query: "Why was I charged ₹999?"

Generated Response: "Please contact customer support."

Run ID: 7f8a-1234-abcd-5678
```

The ID above is illustrative.

Later, when the customer reports that the response was unhelpful, your application can attach that feedback to the corresponding execution.

**What does `collect_runs()` do?**

It captures traced runs produced during the execution context, allowing your code to retrieve their IDs.

Your code uses:

```python
cb.traced_runs[0].id
```

to retrieve the first captured run's ID, which it assumes is the root execution.

One technical detail: this assumes that at least one traced run was captured. In production code, you should validate that `cb.traced_runs` is not empty before indexing it.

### Component 3: Recording User Feedback

Your function:

```python
def record_user_feedback(
    client: Client,
    run_id: str,
    is_positive: bool,
    user_comment: str = ""
):
```

Its job is to associate the user's feedback with the execution identified by `run_id`.

The key operation is:

```python
client.create_feedback(
    run_id=run_id,
    key="user_thumbs",
    score=1.0 if is_positive else 0.0,
    comment=user_comment,
    source_info={"source": "customer_portal_ui"}
)
```

Let's understand the fields.

| Field         | Meaning                                                            |
| ------------- | ------------------------------------------------------------------ |
| `run_id`      | Identifies the execution receiving the feedback.                   |
| `key`         | Names the feedback metric, here `user_thumbs`.                     |
| `score`       | Stores `1.0` for positive feedback or `0.0` for negative feedback. |
| `comment`     | Stores the user's explanation.                                     |
| `source_info` | Records where the feedback originated.                             |

For positive feedback:

```python
is_positive=True
```

The score becomes `1.0`.

For negative feedback:

```python
is_positive=False
```

The score becomes `0.0`.

Your application also records a separate feedback item when the user is unhappy:

```python
client.create_feedback(
    run_id=run_id,
    key="triage_required",
    score=1.0,
    comment="User reported unhelpful response; flagged for human inspection."
)
```

This second feedback item acts as a **triage flag**.

It indicates that the execution should be considered for human review.

However, creating this flag does not automatically put the execution into an Annotation Queue. Your code performs that operation separately.

### Component 4: Annotation Queue

Your function:

```python
def route_to_annotation_queue(client: Client, run_id: str):
```

Its responsibility is to send the problematic execution to a queue for human inspection.

First, the code searches for an existing queue:

```python
queues = list(
    client.list_annotation_queues(name=QUEUE_NAME)
)
```

If one exists, the code reuses it.

Otherwise, it creates a queue:

```python
queue = client.create_annotation_queue(
    name=QUEUE_NAME,
    description="Queue for reviewing flagged customer queries and negative feedback traces."
)
```

The queue is named:

```python
QUEUE_NAME = "Support Triage - Review Queue"
```

Finally, the code adds the problematic run:

```python
client.add_runs_to_annotation_queue(
    queue_id=queue.id,
    run_ids=[run_id]
)
```

**Think of an Annotation Queue as a team's pending-review inbox.**

For example:

| Run   | User Feedback       | Action                                        |
| ----- | ------------------- | --------------------------------------------- |
| Run A | 👍 Helpful          | No review needed under this workflow's rules. |
| Run B | 👎 Unhelpful        | Add to the review queue.                      |
| Run C | 👎 Incorrect answer | Add to the review queue.                      |
| Run D | 👍 Helpful          | No review needed under this workflow's rules. |

The queue doesn't fix the AI response automatically. It organizes executions so that a human can investigate and annotate them.

A human reviewer might discover that the AI needs better instructions, access to the correct data, improved retrieval, or a different response-generation strategy.

### Component 5: The Main Function

Your `main()` function connects all the components.

It runs two scenarios.

**Scenario A: Successful interaction**

```python
run_id_good, _ = run_application_and_capture_id(
    "How do I reset my password?"
)

record_user_feedback(
    client,
    run_id_good,
    is_positive=True,
    user_comment="Fast and accurate!"
)
```

The flow is:

```text
Question
   ↓
LLM generates answer
   ↓
Capture run_id
   ↓
Record positive feedback
   ↓
Finish
```

**Scenario B: Problematic interaction**

```python
run_id_bad, _ = run_application_and_capture_id(
    "My billing charge of $999.00 on invoice #INV-492 is wrong!"
)

record_user_feedback(
    client,
    run_id_bad,
    is_positive=False,
    user_comment="Didn't answer why the charge was made."
)

route_to_annotation_queue(client, run_id_bad)
```

The flow is:

```text
Question
   ↓
LLM generates answer
   ↓
Capture run_id
   ↓
Record negative feedback
   ↓
Mark for triage
   ↓
Add run to Annotation Queue
   ↓
Human reviews the execution
```

One important distinction: your example does not automatically evaluate whether the answer is good or bad. It uses a predefined scenario in which the application receives negative feedback.

In a real application, the user's actual feedback would trigger the appropriate path.

# 5. One Important Technical Distinction

Sir, there's a difference between what your code currently implements and what a complete production feedback system would do.

Your code currently implements a **feedback-and-triage workflow**, not a complete automated learning loop.

It captures feedback, flags negative interactions, and sends them for review.

It does not automatically retrain the model or change its behavior based on the feedback.

A more complete system might work like this:

1. Collect feedback from users.
2. Send problematic executions to human reviewers.
3. Have reviewers label the correct answer or identify the failure.
4. Store those annotations in an evaluation dataset.
5. Use that dataset to evaluate improvements to prompts, retrieval, or models.
6. Deploy changes after appropriate testing.

This is how feedback can contribute to continuous improvement.

Also, the script requires a configured `LANGCHAIN_API_KEY` and a running Ollama model. The API key allows the application to communicate with LangSmith; the local Ollama model generates the response.
